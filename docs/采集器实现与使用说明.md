# 采集器实现与使用说明（README）

> 本次只完成“采集器”这一件事：抓取 Open Food Facts 的零食原始数据并保存到本地文件。
> 未做数据库写入、清洗、配料解析、后端接口，这些属于后续阶段。

## 1. 本次新增了什么

| 文件 | 作用 |
|---|---|
| `crawler/off_crawler.py` | 采集器主程序，只使用 Python 标准库，无需安装第三方包 |
| `crawler/config.json` | 默认配置：国家、品类、分页、限速、重试、输出目录 |
| `docs/采集器实现与使用说明.md` | 本文档 |

## 2. 采集器是做什么的

从 Open Food Facts 公开 API 按品类分页抓取中国零食的原始标签数据，包括产品名称、品牌、配料表、过敏原、添加剂标签、营养成分等，然后：

1. 把每一页 API 原始响应原样保存为 JSON 文件；
2. 把去重后的产品逐行写入 `products.jsonl`；
3. 记录断点、运行统计和日志，支持中断后继续跑。

数据源信息与数据库中的 `biz_data_source` 对应：

| 项目 | 值 |
|---|---|
| 数据源 | Open Food Facts（`biz_data_source.id = 1`） |
| 接口 | `https://world.openfoodfacts.org/api/v2/search` |
| 许可 | ODbL 开放数据库许可，须署名 |
| 限速 | 匿名约 15 请求/分钟/IP，需自定义 User-Agent |

## 3. 环境要求

- Python 3.7 及以上；
- 不需要 `pip install`，脚本只用标准库；
- 能访问 `world.openfoodfacts.org`。

## 4. 第一次使用

### 4.1 先改联系方式

打开 `crawler/config.json`，把 `user_agent` 里的 `your-email@example.com` 改成自己的邮箱。Open Food Facts 要求 User-Agent 中带联系方式，否则更容易被限流。

### 4.2 小样本试跑

在项目根目录执行：

```bash
python crawler/off_crawler.py --categories en:snacks --page-size 5 --max-pages 2 --delay 4
```

含义：只抓 `en:snacks` 这个品类的前 2 页，每页 5 条，两次请求间隔 4 秒，输出到默认目录 `crawler/output`。

### 4.3 正式采集

```bash
python crawler/off_crawler.py
```

默认按 `config.json` 里的 7 个品类采集，每页 100 条，直到每个品类抓完。由于 Open Food Facts 的 503 比较频繁，正式采集耗时可能较长，属于外部服务限制。

### 4.4 断点续跑

直接再执行一次同样的命令即可：

```bash
python crawler/off_crawler.py
```

`state.json` 会记录每个品类下一页的页码；已经下载过的页面文件会直接复用，不会重复请求。

### 4.5 重新开始

```bash
python crawler/off_crawler.py --reset
```

清空 `state.json`、`crawl_summary.json`、`products.jsonl`，但保留 `raw/pages` 页面缓存，所以不会重新下载已经抓过的页面。

### 4.6 查看帮助

```bash
python crawler/off_crawler.py --help
```

## 5. 参数说明

| 参数 | 说明 |
|---|---|
| `--config` | 配置文件路径，默认 `crawler/config.json` |
| `--categories` | 逗号分隔的品类，例如 `en:snacks,en:biscuits` |
| `--country` | 国家/地区标签，默认 `en:china` |
| `--page-size` | 每页条数，最大 100 |
| `--max-pages` | 每个品类本次最多抓几页，0 表示不限 |
| `--delay` | 两次请求的最小间隔（秒），默认 4 |
| `--backoff` | 重试退避的基准秒数，默认 10 |
| `--timeout` | 单次请求超时（秒），默认 30 |
| `--max-retries` | 失败最大重试次数，默认 5 |
| `--output-dir` | 输出目录，默认 `crawler/output` |
| `--reset` | 清空断点与产品汇总后重新开始（保留页面缓存） |
| `--log-level` | 日志级别：DEBUG / INFO / WARNING / ERROR |

## 6. 输出目录

```text
crawler/output/
├── raw/
│   └── pages/
│       ├── en_snacks_page_0001.json
│       ├── en_snacks_page_0002.json
│       └── ...
├── products.jsonl
├── state.json
├── crawl_summary.json
└── crawl.log
```

| 文件 | 说明 |
|---|---|
| `raw/pages/*.json` | 每一页 API 的原始响应，原样保存，便于追溯 |
| `products.jsonl` | 去重后的产品，一行一个原始产品 JSON |
| `state.json` | 断点：每个品类的下一页页码、是否完成 |
| `crawl_summary.json` | 本次运行的统计：页数、请求数、失败数、新增数等 |
| `crawl.log` | 运行日志，包括每次请求和重试 |

## 7. 关键机制

### 7.1 限速

每次请求前检查距离上次请求的时间，不足 `delay_seconds` 就等待。默认 4 秒，对应 Open Food Facts 约 15 请求/分钟的限制。

### 7.2 失败重试

以下情况会重试：

- HTTP 408、425、429、500、502、503、504；
- 网络错误、超时、响应不是合法 JSON。

退避时间按 `backoff_base_seconds × 2^(尝试次数-1)` 计算，默认大约为 10、20、40、80 秒，最多重试 5 次；如果服务器返回 `Retry-After`，会取两者中更大的等待时间。

### 7.3 断点续跑

每抓完一页就更新 `state.json`，先写临时文件再替换，避免中途退出留下半个 JSON。再次运行时：

- 已完成品类直接跳过；
- 未完成品类从记录的下一页继续；
- 已存在的页面文件直接复用，不重复请求。

### 7.4 去重

- 优先用产品条码 `code` 作为去重键；
- 没有条码时，用整条产品 JSON 的 SHA-256 作为键；
- 去重范围是全部品类，因此同一产品出现在多个品类中只保留一次。

### 7.5 原始数据不变

采集器不对字段做清洗、改名或类型转换。`raw/pages` 和 `products.jsonl` 中保存的都是 API 返回的原始内容，后续清洗阶段再处理。

## 8. 与数据库的衔接（下一步，不在本次范围）

本次采集器**不直接写数据库**，避免和后续 Java 后端、清洗程序耦合。建议下一步写一个导入脚本，把 `products.jsonl` 导入原始层：

### 8.1 `biz_crawl_task`

每个品类的一次运行可以记一条：

| 字段 | 取值建议 |
|---|---|
| `source_id` | `1`（Open Food Facts） |
| `keyword` | 品类标签，如 `en:snacks` |
| `request_config` | 本次的分页、限速、重试配置 JSON 快照 |
| `status` | `SUCCESS` 或 `PARTIAL` |
| `request_count` | `crawl_summary.json` 中的 `requests` |
| `success_count` | 成功处理的页数 |
| `fail_count` | 失败请求数 |
| `insert_count` | 新增原始记录数 |
| `start_time` / `end_time` | 本次运行起止时间 |

### 8.2 `biz_raw_record`

建议**一条产品记一条原始记录**：

| 字段 | 取值建议 |
|---|---|
| `task_id` | 对应的采集任务 ID |
| `source_id` | `1` |
| `source_url` | 产品 JSON 里的 `url` 字段；若为空，用该页的 API 请求 URL 兜底（该字段不允许为空） |
| `source_record_key` | 产品条码 `code` |
| `http_status` | `200` |
| `crawl_status` | `SUCCESS` |
| `raw_content` | 该行产品 JSON 原样写入 JSON 字段 |
| `content_hash` | 该行 JSON 字符串的 SHA-256（64 位十六进制） |
| `fetched_at` | 该页的采集时间 |

数据库已有唯一键 `(source_id, content_hash)`，导入时按这个键做幂等，重复导入不会产生重复记录。

> 说明：`raw/pages` 保留的是“页级”原始响应，适合追溯和重跑；入库时建议按“产品级”写入 `biz_raw_record`，这样去重粒度和后续解析粒度一致。

## 9. 已验证内容（2026-11-26）

- 运行环境：Python 3.7.4；
- API 连通性：`en:snacks + en:china` 返回 `count = 180`（测试时点）；
- 小样本试跑：`--page-size 5 --max-pages 2`，成功抓取 2 页共 10 条；
- 断点续跑：第二次运行从第 3 页开始，没有重复抓前两页；
- 失败重试：第 3 页遇到连续 4 次 503，按约 10、20、40、80 秒退避后第 5 次成功；
- 去重：15 条产品条码均不重复；
- 数据质量抽样（15 条）：
  - 12 条有配料表文本；
  - 15 条有营养成分字段；
  - 8 条有添加剂标签；
  - 部分产品缺少中文名称，后续解析需要处理。

## 10. 已知限制

- 只采集 Open Food Facts，不包含抽检公告和电商详情页；
- 只保存原始数据，不写数据库、不清洗、不解析配料；
- Open Food Facts 的 503 较频繁，正式采集需要较长时间；
- 中国零食在 Open Food Facts 中的覆盖率有限，部分产品字段缺失；
- 单 IP 受约 15 请求/分钟限制，未做代理或多 IP 方案。

## 11. 下一步建议

1. 写导入脚本：`products.jsonl` → `biz_crawl_task` / `biz_raw_record`；
2. 清洗整合：原始层 → `biz_product` / `biz_label` / `biz_label_nutrition`；
3. 配料解析：生成 `biz_product_ingredient` 和待确认队列；
4. Java 后端读取标准层，向前端提供 `/api/*` 接口。

以上第 1～4 项均不在本次“只做采集器”的范围内。
