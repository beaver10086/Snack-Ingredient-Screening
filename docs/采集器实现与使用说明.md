# 采集器实现与使用说明（README）

> 本次只完成“采集器”这一件事：抓取 Open Food Facts 的零食原始数据并保存到本地文件。
> 未做数据库写入、清洗、配料解析、后端接口，这些属于后续阶段。
>
> 本文按当前代码 `crawler/off_crawler.py` 与 `crawler/config.json` 的实际实现编写，命令行行为以第 5～7 节为准。

## 1. 本次新增了什么

| 文件 | 作用 |
|---|---|
| `crawler/off_crawler.py` | 采集器主程序，只使用 Python 标准库，无需安装第三方包 |
| `crawler/config.json` | 默认配置：国家、品类、分页、限速、重试、输出目录 |
| `docs/采集器实现与使用说明.md` | 本文档 |

## 2. 采集器是做什么的

从 Open Food Facts 公开 API 按“品类 + 国家/地区”分页抓取零食的原始标签数据，然后：

1. 把每一页 API 响应原样保存为 JSON 文件；
2. 把去重后的产品逐行写入 `products.jsonl`；
3. 记录断点、运行统计和日志，支持中断后继续跑。

实际请求只取代码 `FIELDS` 白名单中的字段，减少响应体积：

```text
code, product_name, product_name_zh, generic_name, brands, categories_tags,
ingredients_text, ingredients_text_zh, allergens_tags, additives_tags,
nutriments, quantity, serving_size, url, last_modified_t, countries_tags
```

也就是说，产品名称、品牌、配料表、过敏原、添加剂标签、营养成分等都在采集范围内，但**白名单以外的字段不会被抓取**。

数据源信息与数据库中的 `biz_data_source` 对应：

| 项目 | 值 |
|---|---|
| 数据源 | Open Food Facts（`biz_data_source.id = 1`） |
| 接口 | `https://world.openfoodfacts.org/api/v2/search` |
| 许可 | ODbL 开放数据库许可，须署名 |
| 限速 | 匿名约 15 请求/分钟/IP，需自定义 User-Agent |

## 3. 环境要求

- Python 3.7 及以上；
- 不需要 `pip install`，脚本只用标准库；
- 能访问 `world.openfoodfacts.org`。

## 4. 第一次使用

### 4.1 先改联系方式

打开 `crawler/config.json`，把 `user_agent` 里的 `your-email@example.com` 改成自己的邮箱。Open Food Facts 要求 User-Agent 中带联系方式，否则更容易被限流。

代码中对此只做**警告**（日志里提示修改联系方式），不会阻止运行。

### 4.2 小样本试跑

在项目根目录执行：

```bash
python crawler/off_crawler.py --categories en:snacks --page-size 5 --max-pages 2 --delay 4
```

含义：只抓 `en:snacks` 这个品类的前 2 页，每页 5 条，两次请求间隔 4 秒，输出到默认目录 `crawler/output`。

注意：输出目录以及 `config.json` 中的 `output_dir` 都是相对 `crawler/` 目录解析的，所以默认值 `output` 实际落在 `crawler/output`。

### 4.3 正式采集

```bash
python crawler/off_crawler.py
```

默认按 `config.json` 里的 7 个品类采集，每页 100 条，直到每个品类抓完。由于 Open Food Facts 的 503 比较频繁，正式采集耗时可能较长，属于外部服务限制。

### 4.4 断点续跑

直接再执行一次同样的命令即可：

```bash
python crawler/off_crawler.py
```

断点规则：

- `state.json` 记录每个品类的下一页页码、是否完成、已完成页数；已存在的页面文件直接复用，不重复请求；
- 页面缓存损坏（不是合法 JSON）时会自动删除并重新下载；
- 如果本次的**国家标签或每页条数**与上次 `state.json` 中记录的不一致，断点会自动重置，从头开始；
- 用 `--max-pages` 限制本次页数时，达到上限后不标记品类完成，下次从记录的下一页继续。

### 4.5 重新开始

```bash
python crawler/off_crawler.py --reset
```

清空 `state.json`、`crawl_summary.json`、`products.jsonl`，但保留 `raw/pages` 页面缓存，所以不会重新下载已经抓过的页面（缓存中的产品会重新写入 `products.jsonl`）。

### 4.6 查看帮助

```bash
python crawler/off_crawler.py --help
```

### 4.7 中断与退出码

| 场景 | 行为 | 退出码 |
|---|---|---|
| 正常结束 | 写入最终 `state.json` / `crawl_summary.json` | `0` |
| 有品类采集失败 | 记录到该品类的 `error`，继续处理其余品类 | `1` |
| 按 `Ctrl+C` 中断 | 捕获中断信号并在 `finally` 中保存断点 | `130` |

## 5. 参数说明

命令行参数会覆盖 `config.json` 中的同名配置。

| 参数 | 说明 |
|---|---|
| `--config` | 配置文件路径，默认 `crawler/config.json`；文件不存在时使用代码内置默认值 |
| `--categories` | 逗号分隔的品类，例如 `en:snacks,en:biscuits` |
| `--country` | 国家/地区标签，默认 `en:china` |
| `--page-size` | 每页条数，最大 100（代码会钳制到 1～100） |
| `--max-pages` | 每个品类本次最多抓几页，0 表示不限 |
| `--delay` | 两次真实请求的最小间隔（秒），默认 4；复用缓存页时不等待 |
| `--backoff` | 重试退避的基准秒数，默认 10 |
| `--timeout` | 单次请求超时（秒），默认 30 |
| `--max-retries` | 单次请求的最大尝试次数（含首次请求），默认 5；达到后放弃该页并记为品类错误 |
| `--output-dir` | 输出目录，相对路径按 `crawler/` 解析，默认 `crawler/output` |
| `--reset` | 清空断点与产品汇总后重新开始（保留页面缓存） |
| `--log-level` | 日志级别：DEBUG / INFO / WARNING / ERROR，默认 INFO |

`config.json` 的键与默认值：

| 键 | 默认值 | 说明 |
|---|---|---|
| `country` | `en:china` | 国家/地区标签 |
| `categories` | 7 个品类 | `en:snacks`、`en:biscuits`、`en:chocolates`、`en:candies`、`en:nuts`、`en:crisps`、`en:cookies` |
| `page_size` | `100` | 每页条数，最大 100 |
| `max_pages_per_category` | `0` | 每品类本次最多页数，0 不限 |
| `delay_seconds` | `4.0` | 请求最小间隔（秒） |
| `timeout_seconds` | `30` | 请求超时（秒） |
| `max_retries` | `5` | 最大尝试次数（含首次） |
| `backoff_base_seconds` | `10.0` | 退避基准秒数 |
| `user_agent` | `SnackDB-CourseProject/1.0 (...your-email@example.com)` | 需改为自己的联系方式 |
| `output_dir` | `output` | 输出目录，相对 `crawler/` |

## 6. 输出目录

```text
crawler/output/
├── raw/
│   └── pages/
│       ├── en_snacks_page_0001.json
│       ├── en_snacks_page_0002.json
│       └── ...
├── products.jsonl
├── state.json
├── crawl_summary.json
└── crawl.log
```

| 文件 | 说明 |
|---|---|
| `raw/pages/*.json` | 每一页 API 的原始响应，原样保存；文件名是把品类标签中非字母数字字符替换为 `_` 后加 `_page_页码`（4 位补零） |
| `products.jsonl` | 去重后的产品，一行一个产品 JSON（仅白名单字段，中文不转义） |
| `state.json` | 断点：`country`、`page_size`、`updated_at`，以及 `categories[品类] = {next_page, done, pages_done}` |
| `crawl_summary.json` | 本次运行汇总：`started_at` / `finished_at` / `updated_at`、`country`、`page_size`、`delay_seconds`、`categories_requested`、`output_dir`、`total_products_saved`，以及每个品类的统计 |
| `crawl.log` | 运行日志，同时输出到控制台和文件，包括每次请求、重试和错误 |

每个品类的统计字段（`crawl_summary.json` 的 `categories[品类]`）：

| 字段 | 含义 |
|---|---|
| `pages_processed` | 本次处理的页数 |
| `requests` | 实际发起的请求次数（含重试） |
| `failed_requests` | 重试次数（尝试次数 − 1） |
| `products_received` | API 返回的产品条数 |
| `new_products` | 新增写入的产品条数 |
| `duplicates` | 被去重跳过的条数 |
| `done` / `next_page` | 是否完成 / 下次开始的页码 |
| `error` | 该品类失败时的错误摘要（仅出错时出现） |

## 7. 关键机制

### 7.1 限速

每次真实请求前检查距离上次请求的时间，不足 `delay_seconds` 就等待；默认 4 秒，对应 Open Food Facts 约 15 请求/分钟的限制。复用本地页面缓存时不会等待，也不计入请求数。

### 7.2 失败重试

以下情况会重试：

- HTTP 408、425、429、500、502、503、504；其他 HTTP 状态码直接判定为不可重试错误；
- 网络错误、超时，以及响应不是合法 JSON（含 gzip 解码失败）。

单次请求的等待时间按 `min(180, backoff_base_seconds × 2^(尝试次数-1)) + 0~1 秒随机抖动` 计算；若响应带 `Retry-After` 头，则取该值与上述等待时间中较大者。默认基准 10 秒时，前几次等待约为 10～11、20～21、40～41、80～81 秒，单次上限 181 秒。

`--max-retries` 是**总尝试次数**（默认 5，即首次请求 + 最多 4 次重试）。达到上限后抛出错误，当前页的断点不会前进，下次运行会从同一页重试；该品类后续页面不再抓取，但其他品类继续。

### 7.3 断点续跑

每处理完一页就更新 `state.json`，先写 `.tmp` 临时文件再替换，避免中途退出留下半个 JSON。再次运行时：

- 已完成品类直接跳过；
- 未完成品类从记录的下一页继续；
- 已存在且合法的页面文件直接复用，不重复请求；
- 国家标签或每页条数与上次不一致时，断点整体重置。

一个品类在以下任一情况被标记为完成：

1. 本页没有返回产品；
2. 已达到 API 返回的 `count`（`页码 × 每页条数 ≥ count`）；
3. 本页产品数少于每页条数；
4. 达到 `--max-pages` 上限时**不算完成**，只保留断点，下次继续。

### 7.4 去重

- 优先用产品条码 `code` 作为去重键；
- 没有条码时，用整条产品 JSON 按 `sort_keys=True` 序列化后的 SHA-256，并加前缀 `hash:`；
- 每次启动先读取已有的 `products.jsonl` 重建去重集合，因此去重范围横跨全部品类以及历次运行；
- `products.jsonl` 中同一产品只保留第一次出现的那条。

### 7.5 原始数据不变

采集器只对 API 返回的字段做“是否请求”的筛选（第 2 节白名单），不做清洗、改名或类型转换。`raw/pages` 和 `products.jsonl` 中保存的都是 API 返回字段的原样内容，后续清洗阶段再处理。

### 7.6 退出码

| 退出码 | 含义 |
|---|---|
| `0` | 所有品类正常结束 |
| `1` | 至少一个品类出现不可恢复错误（详见 `crawl_summary.json` 的 `error`） |
| `130` | 用户按 `Ctrl+C` 中断，断点已保存 |

## 8. 与数据库的衔接（下一步，不在本次范围）

本次采集器**不直接写数据库**，避免和后续 Java 后端、清洗程序耦合。建议下一步写一个导入脚本，把 `products.jsonl` 导入原始层：

### 8.1 `biz_crawl_task`

每个品类的一次运行可以记一条：

| 字段 | 取值建议 |
|---|---|
| `source_id` | `1`（Open Food Facts） |
| `keyword` | 品类标签，如 `en:snacks` |
| `request_config` | 本次的分页、限速、重试配置 JSON 快照 |
| `status` | `SUCCESS` 或 `PARTIAL` |
| `request_count` | `crawl_summary.json` 中的 `requests` |
| `success_count` | 成功处理的页数 |
| `fail_count` | 失败请求数（`failed_requests`） |
| `insert_count` | 新增原始记录数（`new_products`） |
| `start_time` / `end_time` | `crawl_summary.json` 中的 `started_at` / `finished_at` |

### 8.2 `biz_raw_record`

建议**一条产品记一条原始记录**：

| 字段 | 取值建议 |
|---|---|
| `task_id` | 对应的采集任务 ID |
| `source_id` | `1` |
| `source_url` | 产品 JSON 里的 `url` 字段；若为空，用该页的 API 请求 URL 兜底（该字段不允许为空） |
| `source_record_key` | 产品条码 `code` |
| `http_status` | `200` |
| `crawl_status` | `SUCCESS` |
| `raw_content` | 该行产品 JSON 原样写入 JSON 字段（字段范围见第 2 节白名单） |
| `content_hash` | 该行 JSON 字符串的 SHA-256（64 位十六进制） |
| `fetched_at` | 该页的采集时间 |

数据库已有唯一键 `(source_id, content_hash)`，导入时按这个键做幂等，重复导入不会产生重复记录。

> 说明 1：`raw/pages` 保留的是“页级”原始响应，适合追溯和重跑；入库时建议按“产品级”写入 `biz_raw_record`，这样去重粒度和后续解析粒度一致。
>
> 说明 2：当前 `products.jsonl` 没有保存每条产品所属页面的请求 URL 和精确抓取时间，导入脚本需要自行从页面文件时间或汇总文件推断，或在后续版本中由采集器补写这两个字段。

## 9. 历史试跑记录（2026-11-26）

以下是当时的手工试跑结果，仅作参考；代码的实际行为以第 5～7 节为准：

- 运行环境：Python 3.7.4；
- API 连通性：`en:snacks + en:china` 返回 `count = 180`（测试时点）；
- 小样本试跑：`--page-size 5 --max-pages 2`，成功抓取 2 页共 10 条；
- 断点续跑：第二次运行从第 3 页开始，没有重复抓前两页；
- 失败重试：第 3 页遇到连续 4 次 503，按退避后第 5 次成功；
- 去重：15 条产品条码均不重复；
- 数据质量抽样（15 条）：
  - 12 条有配料表文本；
  - 15 条有营养成分字段；
  - 8 条有添加剂标签；
  - 部分产品缺少中文名称，后续解析需要处理。

## 10. 已知限制

- 只采集 Open Food Facts，不包含抽检公告和电商详情页；
- 只保存原始数据，不写数据库、不清洗、不解析配料；
- 只请求第 2 节列出的字段白名单，其他 API 字段不抓取；
- `--max-retries` 是总尝试次数而非“首次失败后的重试次数”；
- 单页彻底失败后该品类剩余页不再抓取，其他品类仍继续；
- Open Food Facts 的 503 较频繁，正式采集需要较长时间；
- 中国零食在 Open Food Facts 中的覆盖率有限，部分产品字段缺失；
- 单 IP 受约 15 请求/分钟限制，未做代理或多 IP 方案。
