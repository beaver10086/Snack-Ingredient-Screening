# 后续规划 × 当前页面 对照表

> 用途：汇报时说明"我们现在做到哪、之后要做什么、以及之后的事其实已经被现在的页面预埋好了"。
> 每一行的「当前页面锚点」都是你屏幕上**已经能看到**的东西，方便你边指边讲。

## 一、总览：从前端框架到数据库系统的路线图

| 阶段 | 后续任务 | 当前页面哪里已体现 | 之后要交付什么 |
|---|---|---|---|
| ① 建表 | 物理建表（~20 张表，3NF） | 所有页面的字段都对齐数据字典第 6 节 | 可执行 SQL 建表脚本（验收 A1） |
| ② 采集 | 采集后端写原始层 | 「数据源与采集」页：数据源登记、任务状态 | Python 采集器 + `raw_record` 原始层 |
| ③ 整合 | 清洗、去重、多源合并 | 「产品检索」页：每个产品带"来源数" | `product` / `product_source` 合并逻辑 |
| ④ 解析 | 配料拆分与词典 | 「配料与添加剂」页：待确认队列 | `product_ingredient` / `ingredient_alias` |
| ⑤ 规则 | 法规规则库 + 版本化 | 「法规与规则库」页：R1~R6 + 使用限量 | `check_rule` / `additive_usage_limit` 落表 |
| ⑥ 筛查 | 规则驱动筛查引擎 | 「合规筛查」页：批次 + 结果列表 | `check_run` / `check_result` 真实产出 |

## 二、逐任务详解（带"汇报时怎么说"）

### ① 建库建表
- **当前页面锚点**：所有页面。比如「产品检索」里显示的 `gb2760_code`、"来源数"等字段，命名直接取自需求文档第 6 节数据字典。
- **之后做什么**：把 `data_source`、`product`、`additive`、`check_rule`、`check_result` 等约 20 张表落成 SQL，满足 3NF、主外键、约束（DB-2）。
- **汇报衔接句**："大家看这些字段名，不是我们随便起的，而是已经对齐了数据库的数据字典——也就是说表结构在我们做前端时就已经规划好了。"

### ② 采集后端 → 原始层
- **当前页面锚点**：「数据源与采集」页。4 类数据源已登记（开放库/电商/官网/抽检公告），采集任务有"成功/运行中/失败"状态，且标注了限速、robots 协议。
- **之后做什么**：用 Python（requests/Scrapy + pandas + OCR）把外网数据抓下来，原样写入 `raw_record` 原始层（采什么存什么、可溯源）。
- **汇报衔接句**："这页的采集任务界面，就是以后采集后端要填充的数据；原始层我们会把网页原文/JSON 原封不动存下来，保证任何结论都能溯源。"

### ③ 清洗与多源整合
- **当前页面锚点**：「产品检索」页。每个产品下面有"来源数"（如乐事薯片 3 个来源），暗示多源要去重合并。
- **之后做什么**：以条形码为主键、无条码用"品牌+名称+规格"相似度匹配，合并成唯一 `product`，并记 `product_source` 映射关系、标记冲突与缺失（FR-2）。
- **汇报衔接句**："一个产品可能来自多个数据源，这页的'来源数'就是为了提示——下一步要做多源去重和合并，确定采用值。"

### ④ 配料解析与词典
- **当前页面锚点**：「配料与添加剂」页。右侧"待人工确认队列"（脱氢乙酸钠、酵母抽提物…），左侧添加剂清单含"禁用"标记（二氧化钛）。
- **之后做什么**：实现配料表拆分、括号嵌套解析、同义词/INS 号映射，落到 `product_ingredient` 与 `ingredient_alias`；识别不了的进待确认队列（FR-3）。
- **汇报衔接句**："这页的待确认队列，就是解析引擎的'兜底'——识别不了的先挂起等人确认，绝不乱判，对应需求 FR-3.6。"

### ⑤ 法规规则库 + 版本化
- **当前页面锚点**：「法规与规则库」页。已列出 GB 2760 / GB 7718 / GB 28050 三条法规，R1~R6 六类规则，以及"使用限量"表（如山梨酸钾 0.075 g/kg）。
- **之后做什么**：把规则和限量写进 `check_rule` / `additive_usage_limit` 表，标准更新时**新增版本**而非覆盖，筛查结果记录所用版本（DB-4/DB-5）。
- **汇报衔接句**："重点看——这些阈值现在写在页面里，以后是存在数据库的规则表里的，程序不写死。国标一更新，我们只加一条新版本数据。"

### ⑥ 合规筛查引擎
- **当前页面锚点**：「合规筛查」页。左侧筛查批次（run#31 全量 2146 件、命中 186），右侧结果含"违规/疑似/提示"三级、证据链、复核状态。
- **之后做什么**：用 SQL/存储过程实现 R1~R6，产出真实 `check_run` / `check_result`；无含量数据只给风险提示、有检出值才判超标（FR-5）。
- **汇报衔接句**："这页现在是演示数据，但每条结果的结构——产品、规则、证据、版本、复核——就是筛查引擎以后要真实产出的样子，而且可追溯。"

### ⑦ 统计视图与报告
- **当前页面锚点**：「统计与报告」页。三类问题分布环形图、按品类占比、高频添加剂 TOP 排行。
- **之后做什么**：落成 DB-7 要求的三个视图（产品配料宽视图、问题产品汇总视图、添加剂使用频次视图），并支持 CSV/Excel 导出（FR-7）。
- **汇报衔接句**："这三个图，背后就是数据库里要建的三个聚合视图，前端已经把展示形态定好了。"

### ⑧ 系统管理
- **当前页面锚点**：「系统管理」页。三种角色（管理员/数据维护员/分析员）、操作日志列表。
- **之后做什么**：落地 `sys_user` / `sys_log`，实现分权与操作留痕（FR-8）。
- **汇报衔接句**："权限和日志界面已经留好，下一步只是把操作真正写进数据库的日志表。"

### ⑨ 工程化（索引/事务/备份/性能）
- **当前页面锚点**：「仪表盘」页。聚合数字（产品数、规则数、覆盖率）本身就依赖后端查询性能。
- **之后做什么**：建索引（DB-3）、导入合并用事务（DB-6）、备份恢复脚本（DB-10）、EXPLAIN 性能对比（A5）。
- **汇报衔接句**："仪表盘这些汇总数字，以后要快就得靠索引和查询优化，这部分是高级数据库课的重点工程项。"

### ⑩ 前后端对接
- **当前页面锚点**：全局。`src/api/index.js` 现在是 `Promise.resolve(MOCK.x)`，文件头已写明替换方式。
- **之后做什么**：后端提供 `/api/*` 端点，把 `api/index.js` 的函数体换成 `http.get(...)`，视图层零改动。
- **汇报衔接句**："我们特意把接口层和演示数据分开了，所以数据库和后端做好后，前端几乎不用改——这就是框架'可扩展'的意义。"

## 三、一句话总结（汇报收尾用）

"我们现在交付的前端框架，已经把每个模块的数据契约和展示形态定义清楚；后续只要按这张表，把页面背后的演示数据换成真实的关系数据库与采集/筛查后端，系统就能从'框架演示'升级为'可用系统'。"
