## 演示 2：数据可溯源（讲"每条信息都能追到出处"）

```sql
SELECT p.product_name, ds.source_name, rr.source_url,
       l.allergen_labeled, n.sodium_mg, n.sugar_g
FROM biz_product p
JOIN biz_label l ON l.product_id = p.id AND l.is_adopted = 1
JOIN biz_data_source ds ON ds.id = l.source_id
JOIN biz_raw_record rr ON rr.id = l.raw_id
LEFT JOIN biz_label_nutrition n ON n.label_id = l.id
WHERE p.id = 1;
```

预期输出：

| product_name | source_name | source_url | allergen_labeled | sodium_mg | sugar_g |
|---|---|---|---|---|---|
| 乐事经典原味薯片 70g | Open Food Facts | https://world.openfoodfacts.org/api/v2/product/7622210449283 | 1 | 520.000 | NULL |

**讲解词**：
> 一条 SQL 把整条溯源链串起来：产品 → 来源标签 → 原始采集记录 URL → 结构化营养。糖是 NULL，因为来源没标注，我们如实留空，不编造。这条链路对应需求里的可追溯性。

## 演示 3：FR-9 三态筛选（本次最重要的业务查询）

```sql
SELECT product_name,
  CASE
    WHEN allergen_labeled = 0 OR sodium_mg IS NULL OR sugar_g IS NULL THEN 'INSUFFICIENT_INFO'
    WHEN EXISTS (
      SELECT 1 FROM v_product_ingredient_detail d
      WHERE d.product_id = v.product_id AND d.allergen_type = '麸质谷物'
    ) OR sodium_mg > 600 OR sugar_g > 25 THEN 'UNFIT'
    ELSE 'FIT'
  END AS filter_state,
  allergen_labeled, sodium_mg, sugar_g
FROM v_product_adopted_overview v
ORDER BY product_name;
```

预期输出（6 款产品）：

| product_name | filter_state | allergen_labeled | sodium_mg | sugar_g |
|---|---|---|---|---|
| 乐事经典原味薯片 70g | INSUFFICIENT_INFO | 1 | 520.000 | NULL |
| 低糖全麦苏打饼干 100g | INSUFFICIENT_INFO | 0 | 610.000 | 3.000 |
| 卫龙辣条大面筋 106g | UNFIT | 1 | 980.000 | 12.000 |
| 大白兔奶糖 114g | UNFIT | 1 | 120.000 | 50.000 |
| 奥利奥夹心饼干 97g | UNFIT | 1 | 380.000 | 35.000 |
| 沃隆每日坚果 25g | INSUFFICIENT_INFO | 1 | 5.000 | NULL |

**讲解词**：
> 这就是前台筛选页背后的核心 SQL，跑在真实数据上。含麸质或钠糖超标的判为 UNFIT；糖没标注、致敏原没标注的判为 INSUFFICIENT_INFO——**我们绝不把信息缺失误判成"适合"**。注意目前没有 FIT 的产品，因为示例数据里每款要么超标要么字段不全。

## 演示 4：添加剂反向检索（讲"配料解析 + 知识库联动"）

```sql
SELECT DISTINCT p.product_name, a.additive_name, a.ins_no, a.function_class
FROM v_product_ingredient_detail d
JOIN biz_product p ON p.id = d.product_id
JOIN biz_additive a ON a.id = d.additive_id
WHERE a.additive_name = '特丁基对苯二酚';
```

预期输出：

| product_name | additive_name | ins_no | function_class |
|---|---|---|---|
| 乐事经典原味薯片 70g | 特丁基对苯二酚 | 319 | 抗氧化剂 |

**讲解词**：
> 查"哪些产品含 TBHQ"，一条 SQL 出来，还带出 INS 编码和功能类别。说明配料解析明细表和添加剂知识库已经真正关联——配料不再是纯文本，而是能查询的关系数据。

## 演示 5：约束真的生效（讲"这不是摆设"）

先开事务，测试后回滚，不污染数据：

```sql
START TRANSACTION;
INSERT INTO biz_label_nutrition (label_id, product_id, basis_type, sodium_mg, nutrition_complete)
VALUES (101, 1, 'per_100g', -5, 0);
```

预期输出：

```
ERROR 3819 (HY000): Check constraint 'chk_nutrition_non_negative' is violated.
```

再测外键：

```sql
INSERT INTO biz_label (product_id, source_id, is_adopted, captured_at)
VALUES (9999, 1, 0, NOW());
```

预期输出：

```
ERROR 1452 (23000): Cannot add or update a child row: a foreign key constraint fails
```

最后回滚：

```sql
ROLLBACK;
SELECT COUNT(*) FROM biz_label;          -- 应为 7，数据未被污染
SELECT COUNT(*) FROM biz_label_nutrition; -- 应为 6
```

**讲解词**：
> 我故意插入非法的负数营养值和不存在的外键，数据库都拒绝了。说明约束是数据库级真正生效的，不是靠程序自觉。这也是我们坚持用 MySQL 8.0 的原因——低版本会静默忽略 CHECK。

## 现场注意

1. **服务没启动**：双击 `D:\MySQL\start-mysql8.bat`，保持窗口开着。
2. **命令太长怕敲错**：可以先在记事本里准备好，用 mysql 的单行粘贴执行；或提前把上面 5 条查询存成 `.sql` 文件，用 `SOURCE 路径;` 一次跑。
3. **怕现场翻车**：把上面 5 个数据库预期输出各截一张图存手机/备用 PPT；采集器那一步如果网络不通，用提前跑好的 JSON 文件和日志讲。
4. **时间控制**：演示 1~5 全部敲完约 3~4 分钟，采集器演示约 1 分钟；重点是演示 3（三态筛选）、演示 5（约束）和演示 6（真实采集）。
5. **别忘了收尾**：演示完回到前端访客页，说一句"这些查询结果就是前台页面的数据来源，而数据就是刚才采集器从网上拿回来的"，前后呼应，把前端—数据库—采集器串成一条线。
