## 一、开场（约 1 分钟）

（站在屏幕前，先不点页面）

各位老师、同学好，我们是第 X 组，项目是「零食标签数据与查询系统」。

先用半分钟回顾定位。我们最初想做"合规筛查"——用网上数据判断零食违不违规。之前汇报后我们意识到：**不合规产品不会自我标注，公开标签里也没有"检测结果"这个真值**，学生拿不到判定依据。所以我们把问题换掉了：不做判定者，改做信息整理者——**把散落在网上的零食标签整理成结构化的关系数据库，让有过敏、控糖控钠需求的人能查成分、避风险**。

定位改完之后，紧接着就是老师追问的第二个问题：**"数据从哪来？"** 今天这次汇报，我们带来的阶段性成果正好分三层，逐层回答这个问题：

- **第一层，前端**：系统长什么样、能给用户提供什么；
- **第二层，数据库**：数据怎么存、怎么查、怎么保证可信；
- **第三层，也是这次新增的——采集器**：真实数据到底怎么从网上批量拿到。

我会先用一分半展示前端，再用四分钟重点演示数据库，最后用两分钟现场演示采集器，然后讲当前进度和下一步。

## 三、数据库成果展示（约 4 分钟，本次重点之一）

（切到数据库演示窗口，按《数据库演示速查卡》的顺序现场敲命令）

接下来是重点。我们按《需求文档 V2.2》完成了数据库设计，用的是 MySQL 8.0，采用**原始层—标准层—知识与解读层—系统管理层**的分层架构。我现在现场演示四件事：**表结构、数据溯源、三态筛选、约束有效性**。

### 第一件事：19 张表 + 3 个视图，全部建成

（敲 `SHOW FULL TABLES;`，屏幕上出现 19 个 BASE TABLE 和 3 个 VIEW）

老师请看，19 张业务表、3 个查询视图，全部创建成功。它们分四层：
- **原始层**：数据源、采集任务、不可变原始记录——采回来的 JSON 原样存着，还带 SHA-256 摘要去重；
- **标准层**：品牌、品类、产品、标签、结构化营养——同一产品按条码去重，多来源标签分版本留存；
- **知识与解读层**：添加剂知识库、配料词典、关注规则、解读结果；
- **系统管理层**：后台用户和操作日志。

**这个分层就是为了回答老师最关心的问题：数据从哪来、怎么洗、怎么存、怎么查。**

### 第二件事：数据可溯源——每条结论都能追到原始来源

（敲溯源链查询，屏幕上出现乐事薯片那条：来源 Open Food Facts、完整 URL、钠 520mg、糖 NULL）

这是我们的溯源链演示。拿"乐事经典原味薯片"举例：一条 SQL 就能查到它来自哪个数据源、原始记录的 URL 是什么、钠含量多少、糖为什么是 NULL（因为来源没标注）。**从原始采集记录，到标准产品，到标签，到结构化营养，整条链路是通的。** 任何一条展示给用户的信息，都能指回它的原始出处。

### 第三件事：FR-9 三态筛选，在真实数据库上跑通

（敲三态筛选 SQL，屏幕上出现 6 款产品的 FIT / UNFIT / INSUFFICIENT_INFO 结果）

这是前台筛选页背后的那条核心 SQL，现在它跑在真实数据上。请看结果：卫龙辣条、奥利奥、大白兔判为 UNFIT——因为含麸质或钠糖超标；乐事和沃隆坚果判为 INSUFFICIENT_INFO——因为糖含量没标注，**我们没有默认判它"适合"**。这里正好演示了我们的严谨性设计：**信息不足单独成一类，绝不误判。**

（再敲反向检索 SQL：查含 TBHQ 的产品）

再演示一个反向检索：查"哪些产品含特丁基对苯二酚"，一条 SQL 就出来了，还带出它的 INS 编码 319 和功能类别"抗氧化剂"。**这说明配料解析和添加剂知识库已经真正关联起来了**，不是各存各的。

### 第四件事：约束真的生效——证明这不是摆设

（敲 CHECK 约束测试：插入一条钠为负数的记录，屏幕上出现 ERROR 3819；再敲外键测试，出现 ERROR 1452）

最后演示约束。我故意插入一条钠含量为 -5 的非法记录，数据库直接拒绝，报 CHECK 约束冲突；再插入一条引用不存在产品的记录，外键约束也拒绝了。

（语气加重，说这句）

**为什么专门演示这个？因为很多课程作业的表只是把字段列出来，约束是空的。我们的表有真实的主外键、CHECK 约束、非空约束，数据完整性是数据库级别的保证，不是靠程序自觉。** 这也是我们坚持用 MySQL 8.0 的原因——低版本会静默忽略 CHECK 约束。

（总结一下）

以上四件事，就是数据库阶段的阶段性成果：**表建成、数据导入、查询跑通、约束生效**。同时写了初始化和测试数据脚本，任何人拿到三个 SQL 文件按顺序执行，就能完整复现我们的数据库。

## 四、采集器成果展示（约 2~3 分钟，本次新增亮点）

（切到终端，准备现场跑采集器）

接下来这一块是本次新完成的，也是直接回答老师上次那个问题——**"学生从网上到底能不能拿到真实数据？"** 我们的答案是：能，而且是用程序自动拿的。

（先展示 crawler/off_crawler.py 代码，停留几秒）

这是我们写的采集器，490 行 Python，只用标准库，不需要装任何第三方包。它从 Open Food Facts 的公开 API 按品类分页抓取中国零食标签数据。我重点讲四个工程机制——**这四个正好是老师希望看到的"采集任务管理"能力**：

1. **限速**：默认每次请求间隔至少 4 秒，遵守开放 API 约 15 次/分钟的限制；
2. **失败重试**：遇到 503、429 这类错误，按 10、20、40、80 秒指数退避重试，尊重服务器返回的 Retry-After；
3. **断点续跑**：`state.json` 记录每个品类抓到第几页，中断后再次运行直接接着跑，已下载的页面直接复用；
4. **去重**：用条码做主键，没条码的用整条 JSON 的 SHA-256，同一产品跨品类只留一条。

（现场执行小样本采集，命令见速查卡"演示 6"）

现在我现场跑一次小样本：只抓一个品类、一页、5 条。请注意看日志——（指着屏幕）这里出现了 HTTP 503，然后自动等待、重试、成功。**这不是我提前录好的，是现场真实请求。** 抓回来的数据原样存成 JSON 文件，一条产品一行，全部保留原始出处。

（展示 products.jsonl 里的真实数据）

老师请看这几条真实抓回来的数据：有中文配料表、有过敏原标签、有几十个营养字段。比如这条乐事薯片，配料是"马铃薯、植物油、经典原味调味料……"。**这就是我们要的信息——真实存在、公开可得、每条都带来源 URL。**

（语气放慢，说这句关键的）

**同时我们也如实看到数据质量问题：有一条没产品名、有一条配料是德文、还有拼写错误。这恰恰说明下一阶段"清洗整合"和"配料解析"是必须的，不是多余的——采集器负责把数据拿回来，数据库负责把它理干净，这两件事正好串成一条完整的 ETL 流程。**

## 七、答辩常见问题应答（备用）

**Q：数据库到底做完没有？做到什么程度？**
A：设计和实现完成了——19 张表、3 个视图、主外键与 CHECK 约束、初始化与测试数据脚本，已在 MySQL 8.0 导入并跑通核心查询，现场可以演示。还没做的是导入脚本和解析程序，目前库里是 6 条演示数据。

**Q：为什么不用低版本 MySQL？**
A：我们的表用了 CHECK 约束保证数据完整性（比如营养数值非负）。MySQL 5.7 会静默忽略 CHECK，8.0.16 以上才真正生效，所以选了 8.0，刚才现场也演示了约束拒绝非法插入。

**Q：数据到底从哪来？是真爬的吗？**
A：是真爬的。我们写了 490 行的 Python 采集器，从 Open Food Facts 公开 API 按品类分页抓取，遵守限速、失败重试、断点续跑、去重。刚才现场跑了一次小样本，日志里能看到真实的 503 重试过程，抓回来的中文配料表和营养字段都在文件里。数据源采用 ODbL 开放许可，要求署名，我们已在说明文档中标注。

**Q：为什么不爬电商网站？**
A：电商详情页主要是图片配料表，需要 OCR，且有反爬和服务条款限制，投入产出比低。开放 API 有结构化的配料和营养字段、许可清晰，更适合课程项目。我们也在说明文档里如实写了这个限制。

**Q：采集器抓的数据直接进数据库了吗？**
A：还没有。采集器按原始层设计理念，先把 API 原始 JSON 原样存成文件（可追溯、可重跑），下一步写导入脚本按 SHA-256 幂等写入 `biz_raw_record`。这样设计是为了让采集和入库解耦，采集程序不依赖数据库结构。

**Q：采集到的数据质量怎么样？**
A：真实数据确实有瑕疵——我们抽样就发现了缺产品名、德文配料、拼写错误等情况。这正是下一阶段清洗整合和配料解析要解决的，我们在采集说明文档里如实记录了数据质量抽样结果。

**Q：前端连数据库了吗？**
A：还没有。前端 api 层现在是演示数据，但字段完全按数据字典设计。数据库建好后，后端提供接口，替换 api 层即可，页面不用重做——这正是当初分层设计的好处。

**Q：只有 6 条数据，够吗？**
A：库里这是演示数据，用来验证表结构和查询逻辑。数据上量靠采集器，目标 300~500 条真实数据，先灌进原始层再逐步清洗。我们更看重每条可追溯到来源，而不是堆量。

**Q：为什么不判定合规、只做信息整理？**
A：学生拿不到判定真值——标签不会写"我违规"，抽检公告只覆盖极少数样本。所以我们改成信息整理与查询服务，这也是需求文档 1.2 节明确写的修订理由，并且全程不做违法定性。

**Q：三态筛选里为什么有"信息不足"？**
A：因为真实数据里营养和致敏原字段经常缺失。如果把缺失当"没有"，会把不适合的产品误判成适合，反而害了用户。所以我们规定：字段缺失一律归"信息不足"，绝不默认判适合。需求 FR-9.4 写死了这条。

**Q：五个人怎么分工？**
A：按数据流切——采集、清洗、解析、规则解读、应用对接各一人，组长负责数据库设计与总协调。每人都有明确的数据库交付物，谁的产出是谁的输入。
