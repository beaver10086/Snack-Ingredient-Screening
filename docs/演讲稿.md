（站在屏幕前，先不点页面）

各位老师、同学好，我们是第 X 组，项目是「零食标签数据与查询系统」。

先用半分钟回顾定位。我们最初想做"合规筛查"——用网上数据判断零食违不违规。上次汇报后我们意识到：**不合规产品不会自我标注，公开标签里也没有"检测结果"这个真值**，学生拿不到判定依据。所以我们把问题换掉了：不做判定者，改做信息整理者——**把散落在网上的零食标签整理成结构化的关系数据库，让有过敏、控糖控钠需求的人能查成分、避风险**。

今天这次汇报，我们带来的阶段性成果有两部分：**第一，一个可操作的系统前端；第二，也是重点——一套已经建成、导入真实数据、并且跑通了核心查询的数据库。** 我会先用两分钟展示前端，然后重点演示数据库，最后讲当前进度和下一步。

## 三、数据库成果展示（约 5 分钟，本次重点）

（切到数据库演示窗口，按《数据库演示速查卡》的顺序现场敲命令）

接下来是本次汇报的重点。我们按《需求文档 V2.2》完成了数据库设计，用的是 MySQL 8.0，采用**原始层—标准层—知识与解读层—系统管理层**的分层架构。我现在现场演示四件事：**表结构、数据溯源、三态筛选、约束有效性**。

### 第一件事：19 张表 + 3 个视图，全部建成

（敲 `SHOW FULL TABLES;`，屏幕上出现 19 个 BASE TABLE 和 3 个 VIEW）

老师请看，19 张业务表、3 个查询视图，全部创建成功。它们分四层：
- **原始层**：数据源、采集任务、不可变原始记录——采回来的 JSON 原样存着，还带 SHA-256 摘要去重；
- **标准层**：品牌、品类、产品、标签、结构化营养——同一产品按条码去重，多来源标签分版本留存；
- **知识与解读层**：添加剂知识库、配料词典、关注规则、解读结果；
- **系统管理层**：后台用户和操作日志。

**这个分层就是为了回答老师最关心的问题：数据从哪来、怎么洗、怎么存、怎么查。**

### 第二件事：数据可溯源——每条结论都能追到原始来源

（敲溯源链查询，屏幕上出现乐事薯片那条：来源 Open Food Facts、完整 URL、钠 520mg、糖 NULL）

这是我们的溯源链演示。拿"乐事经典原味薯片"举例：一条 SQL 就能查到它来自哪个数据源、原始记录的 URL 是什么、钠含量多少、糖为什么是 NULL（因为来源没标注）。**从原始采集记录，到标准产品，到标签，到结构化营养，整条链路是通的。** 这条对应需求里的可追溯性——任何一条展示给用户的信息，都能指回它的原始出处。

### 第三件事：FR-9 三态筛选，在真实数据库上跑通

（敲三态筛选 SQL，屏幕上出现 6 款产品的 FIT / UNFIT / INSUFFICIENT_INFO 结果）

这是前台筛选页背后的那条核心 SQL，现在它跑在真实数据上。请看结果：卫龙辣条、奥利奥、大白兔判为 UNFIT——因为含麸质或钠糖超标；乐事和沃隆坚果判为 INSUFFICIENT_INFO——因为糖含量没标注，**我们没有默认判它"适合"**。这里正好演示了我们的严谨性设计：**信息不足单独成一类，绝不误判。**

（再敲反向检索 SQL：查含 TBHQ 的产品）

再演示一个反向检索：查"哪些产品含特丁基对苯二酚"，一条 SQL 就出来了，还带出它的 INS 编码 319 和功能类别"抗氧化剂"。**这说明配料解析和添加剂知识库已经真正关联起来了**，不是各存各的。

### 第四件事：约束真的生效——证明这不是摆设

（敲 CHECK 约束测试：插入一条钠为负数的记录，屏幕上出现 ERROR 3819；再敲外键测试，出现 ERROR 1452）

最后演示约束。我故意插入一条钠含量为 -5 的非法记录，数据库直接拒绝，报 CHECK 约束冲突；再插入一条引用不存在产品的记录，外键约束也拒绝了。

（语气加重，说这句）

**为什么专门演示这个？因为很多课程作业的表只是把字段列出来，约束是空的。我们的表有真实的主外键、CHECK 约束、非空约束，数据完整性是数据库级别的保证，不是靠程序自觉。** 这也是我们坚持用 MySQL 8.0 的原因——低版本会静默忽略 CHECK 约束。

（总结一下）

以上四件事，就是数据库阶段的阶段性成果：**表建成、数据导入、查询跑通、约束生效**。同时还写了初始化数据和测试数据脚本，任何人拿到这三个 SQL 文件，按顺序执行，就能完整复现我们的数据库。

## 六、答辩常见问题应答（备用）

**Q：数据库到底做完没有？做到什么程度？**
A：设计和实现完成了——19 张表、3 个视图、主外键与 CHECK 约束、初始化与测试数据脚本，已在 MySQL 8.0 导入并跑通核心查询。现场可以演示。还没做的是采集器和解析程序，目前数据是 6 条示例。

**Q：为什么不用低版本 MySQL？**
A：我们的表用了 CHECK 约束保证数据完整性（比如营养数值非负）。MySQL 5.7 会静默忽略 CHECK，8.0.16 以上才真正生效，所以选了 8.0，刚才现场也演示了约束拒绝非法插入。

**Q：前端连数据库了吗？**
A：还没有。前端 api 层现在是演示数据，但字段完全按数据字典设计。数据库建好后，后端提供接口，替换 api 层即可，页面不用重做——这正是当初分层设计的好处。

**Q：只有 6 条数据，够吗？**
A：这是演示数据，用来验证表结构和查询逻辑。数据上量靠下一步的采集器，目标 300~500 条真实数据。我们更看重每条可追溯到来源，而不是堆量。

**Q：为什么不判定合规、只做信息整理？**
A：学生拿不到判定真值——标签不会写"我违规"，抽检公告只覆盖极少数样本。所以我们改成信息整理与查询服务，这也是需求文档 1.2 节明确写的修订理由，并且全程不做违法定性。

**Q：三态筛选里为什么有"信息不足"？**
A：因为真实数据里营养和致敏原字段经常缺失。如果把缺失当"没有"，会把不适合的产品误判成适合，反而害了用户。所以我们规定：字段缺失一律归"信息不足"，绝不默认判适合。需求 FR-9.4 写死了这条。

**Q：五个人怎么分工？**
A：按数据流切——采集、清洗、解析、规则解读、应用对接各一人，组长负责数据库设计与总协调。每人都有明确的数据库交付物，谁的产出是谁的输入。
