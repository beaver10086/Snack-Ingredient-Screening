## 1 项目背景

### 1.1 背景

零食（薯片、辣条、饼干、糖果、坚果、膨化食品等）消费量大、品牌多、配方更新快。配料表和营养成分表是消费者了解产品成分的主要依据。但目前：

- 配料信息分散在开放食品数据库、品牌官网、监管公告等多个来源，格式不统一、命名不规范（如"柠檬黄""FD&C Yellow 5""INS 102"指向不同写法）；
- 普通消费者难以快速回答"这个产品含有哪些添加剂""两款薯片哪个糖更少""含花生过敏原的产品有哪些"这类问题；
- 过敏体质、控糖控钠等有特定饮食需求的人群，缺乏便捷的工具从配料表中筛选适合自己的产品。

**用户分区设计（V2.2 新增）**：系统面向两类使用者，页面按使用者分区而非按数据流程分区。
- **消费者前台应用区**：面向过敏体质、控糖控钠等普通消费者，免登录、步骤少、术语少，核心是"勾选我的饮食需求 → 一键筛选 → 看懂结果"，追求易用性；
- **后台数据区**：面向数据维护员与分析员，包含采集、清洗整合、配料标准化、知识规则维护、统计报告，允许必要的复杂性以体现数据库技术深度。
两区共享同一套数据与规则（表驱动），前台筛选结果由后台维护的数据支撑，避免"数据库有了但普通人用不上"。

### 1.2 要解决的问题

> **重要修订**：原需求试图"判定产品是否违规"。经课程汇报反馈，该目标对学生项目不可行——不合规产品不会自我标注，公开标签数据不含检测真值，抽检公告仅覆盖极少数被抽检样本。因此本版将问题重新定义为**信息整理与查询服务**，不做违法定性。

本系统要解决的新问题：

1. 如何从公开网络数据源（开放数据库、监管公告）稳定采集零食标签数据？
2. 如何把非结构化的配料表文本解析、标准化为可查询的结构化数据？
3. 如何把添加剂知识、用户个人的饮食关注点组织为可维护的规则数据？
4. 如何支持消费者按成分、品牌、营养、过敏原等维度检索、对比和筛选产品？

### 1.3 术语

| 术语 | 说明 |
|---|---|
| 配料表 | 预包装食品标签上列出的全部配料及添加剂，按加入量递减排列 |
| 食品添加剂 | 为改善品质、延长保质期等加入的物质，如防腐剂、着色剂、甜味剂 |
| INS 号 / CNS 号 | 添加剂的国际编码 / 中国编码 |
| 食品分类号 | GB 2760 中的食品类别编号，用于归类产品 |
| 标签结构化 | 把配料表文本拆分为有序的配料序列并映射到标准名称 |
| 个性化提示 | 根据用户自定义的过敏原、营养阈值对产品给出提示，不构成合规判定 |
| 三态结果 | 前台筛选结果分为适合 / 不适合 / 信息不足；字段缺失不默认判为适合 |
| 消费者前台应用区 | 免登录、面向普通消费者的筛选入口，与后台数据区共享同一数据库 |
| ETL | 抽取（Extract）- 转换（Transform）- 加载（Load），数据采集清洗入库的标准流程 |

## 2 项目目标

### 2.1 总体目标

建设一个面向零食标签的**数据采集 — 存储 — 标准化 — 查询分析**数据库系统，完成课程设计中数据库设计、多源数据整合、查询优化与应用验证的完整闭环。**系统输出为客观标签信息与知识科普，不对产品做违法定性。**

### 2.2 具体目标（可验收）

| 编号 | 目标 | 验收指标 |
|---|---|---|
| G1 | 网络数据采集 | 接入不少于 2 类公开数据源；采集零食产品 **300~500 条**（多品类累加） |
| G2 | 数据质量 | 配料表非空率 ≥ 90%；按条码去重后产品唯一；字段缺失有标记不删除 |
| G3 | 标签结构化 | 配料/添加剂标准名称映射覆盖率 ≥ 80%（抽样人工核对） |
| G4 | 知识库 | 覆盖常见添加剂（防腐剂、着色剂、甜味剂、抗氧化剂等）的功能类别与科普说明 |
| G5 | 查询与对比 | 支持按成分、品牌、品类、营养、过敏原的多维检索与产品横向对比 |
| G6 | 结果可追溯 | 每条产品可追溯到数据源 URL、原始记录、采集时间与所用规则 |
| G7 | 统计分析 | 支持按品类/品牌/添加剂/营养区间的多维统计与导出 |
| G8 | 消费者前台可用性（V2.2 新增） | 普通用户**无需登录、3 次点击内**完成"选饮食需求 → 看筛选结果 → 看懂命中原因"；结果明确区分适合/不适合/信息不足三态，界面不出现条码、FR 编号、批次号等后台术语 |

> 数据规模分别统计原始记录数、去重产品数、配料非空数、营养非空数及解析成功数；“采集记录数”不得等同于“有效标签产品数”。第二产品标签源须先完成可访问性、字段覆盖、条款与样本量验证，验证通过后才纳入自动采集目标；未通过时如实记录限制，不得将人工核对或抽检公告表述为自动标签采集源。

> 说明：原"合规筛查准确率 ≥80%"指标已删除——公开标签数据无判定真值，不设此指标。

## 3 功能性需求

### 3.1 功能模块总览

| 模块 | 编号前缀 | 所属区 | 说明 |
|---|---|---|---|
| 数据源与采集管理 | FR-1 | 后台数据区 | 配置数据源、执行自动采集任务（限速/重试/日志） |
| 数据清洗与整合 | FR-2 | 后台数据区 | 去重、字段规范化、多源合并、质量标记 |
| 配料解析与标准化 | FR-3 | 后台数据区 | 配料表拆分、名称映射、添加剂识别（系统技术核心） |
| 添加剂知识与关注规则 | FR-4 | 后台数据区 | 添加剂知识库、用户自定义过敏原/营养阈值规则 |
| 成分解读与个性化提示 | FR-5 | 后台数据区 | 输出客观信息、科普说明、用户关注命中提示 |
| 查询与对比 | FR-6 | 后台数据区 | 产品检索、反向检索、横向对比（后台专业检索） |
| 统计与报告 | FR-7 | 后台数据区 | 多维统计、数据质量报告、导出 |
| 系统管理 | FR-8 | 后台数据区 | 用户角色、采集任务管理、操作日志 |
| **个性化饮食筛选** | **FR-9** | **消费者前台应用区** | **免登录勾选饮食需求、一键筛选、结果三态与命中原因（V2.2 新增）** |

> 分区原则：前后台不是两套系统，而是同一数据库上的两类视图。前台只暴露 FR-9 与必要的产品详情/知识科普；后台承载 FR-1~FR-8 的全部管理功能。

### 3.10 FR-9 个性化饮食筛选（消费者前台应用区，V2.2 新增）

> 这是本系统与普通消费者直接交互的核心模块。设计目标是让有特定饮食需求的人"不用懂数据库、不用看条码和批次号"就能筛出适合自己的产品。阈值由用户自设，系统只做客观数值比较与配料命中判断，不替用户做健康决策。

| 编号 | 需求描述 | 优先级 |
|---|---|---|
| FR-9.1 | **免登录进入**：消费者无需账号即可使用筛选，不展示后台术语（GTIN、FR 编号、解读批次、规则版本） | 高 |
| FR-9.2 | **勾选饮食需求**：提供常见过敏原勾选项（花生、麸质谷物、乳、大豆、坚果、蛋等）与控糖/控钠开关；阈值可由用户自定义（如钠 ≤ 400 mg/100g），系统不预设健康标准值 | 高 |
| FR-9.3 | **一键筛选**：按勾选条件过滤产品，结果按"适合 / 不适合 / 信息不足"三态展示；排序时"适合"优先 | 高 |
| FR-9.4 | **信息不足单列**：过敏原或营养字段缺失的产品不得默认为"适合"，必须归入"信息不足"并说明缺哪项数据（回应真实数据标注不全的问题） | 高 |
| FR-9.5 | **结果可解释**：每个结果展示命中的关注项、来自配料表/营养成分表的原文证据，用户能看懂"为什么适合/不适合" | 高 |
| FR-9.6 | **查看配料详情**：结果项可展开查看完整配料表、添加剂科普说明；展示来源 URL 以满足可追溯性（G6） | 中 |
| FR-9.7 | **轻量产品对比**：筛选结果中可勾选两款产品横向对比（复用 FR-6.3），便于消费者在货架前做选择 | 中 |
| FR-9.8 | **免责声明固定展示**：前台页面常驻"结果仅供参考，不构成合规判定或健康建议，不替代专业营养指导" | 高 |

> 与 FR-6.4 的关系：FR-6.4 是后台分析员的组合检索工具，可含复杂字段；FR-9 是消费者入口，只暴露与饮食需求相关的少数选项。二者调用同一筛选逻辑，但界面复杂度与术语完全不同。

## 4 非功能性需求

| 类别 | 编号 | 需求 |
|---|---|---|
| 性能 | NFR-1 | 单品检索响应 ≤ 1 秒；多条件组合查询（10 万级配料关联记录）≤ 3 秒 |
| 性能 | NFR-2 | 批量采集 500 件产品在合理时间内完成，支持分批与断点续跑 |
| 数据质量 | NFR-3 | 关键字段（产品名、来源、配料原文）非空；唯一性约束与外键完整性 |
| 一致性 | NFR-4 | 导入、合并、解析写入采用事务；失败可回滚 |
| 可追溯性 | NFR-5 | 任何信息可追溯到原始数据、数据源 URL、规则及版本 |
| 可扩展性 | NFR-6 | 新增数据源、新增知识条目不需修改表结构（表驱动） |
| 可维护性 | NFR-7 | 采集器按数据源模块化；配置化管理；代码与 SQL 脚本纳入版本管理 |
| 合规与伦理 | NFR-8 | 仅采集公开数据；遵守 robots 与站点条款；限速访问；注明数据来源与 ODbL 署名；不绕过登录/反爬 |
| 安全 | NFR-9 | 数据库账号分权；备份策略；敏感配置不入库明文 |
| **结果表述** | NFR-10 | **系统输出为客观标签信息与知识科普，不构成合规判定；"客观事实/知识科普/个人提示"三级在界面和报告中明确区分** |
| 可用性 | NFR-11 | 提供查询界面与操作说明文档 |
| 可用性 | NFR-12 | 消费者前台免登录、筛选主流程不超过 3 次点击；界面不出现后台专业术语（V2.2 新增） |

## 5 数据来源说明

### 5.1 主数据源：Open Food Facts（实测）

| 项目 | 内容 |
|---|---|
| 类型 | 开放众包食品数据库 |
| 端点 | `GET https://world.openfoodfacts.org/api/v2/search` |
| 认证 | 读取免注册，须带自定义 `User-Agent` |
| 实测中国零食存量 | 约 180 条（`countries_tags=en:china` + `categories_tags=en:snacks`） |
| 可用字段 | 条码、名称、品牌、配料表原文、添加剂标签、营养成分、来源 URL |
| 授权 | ODbL 开放数据库许可，须署名；众包数据不保证准确 |
| 限制 | 匿名限速 15 req/min/IP，**实测连续请求返回 503**，须做限速退避 |

**取数策略**：按多个 `categories_tags`（snacks、biscuits、chocolates、candies、nuts 等）分别抓取累加，目标 300~500 条真实数据。

### 5.2 验证数据源：监管抽检公告

| 项目 | 内容 |
|---|---|
| 来源 | 国家市场监督管理总局官网公开通告 |
| 获取方式 | 网页公告 + Excel/PDF 附件解析 |
| 可用字段 | 产品名称、检验项目、检出值、标准限值 |
| 定位 | **规则验证样本**，非配料表数据源；量小（20~50 条） |

### 5.3 补充数据源：电商公开详情页

- 仅作少量人工核对补充（30~50 条），不作主力；
- 不大规模爬取：反爬机制、页面结构易变、配料多为图片需 OCR、条款限制。

### 5.4 数据源使用原则

1. 每个数据源登记名称、URL、获取日期、使用条款说明；
2. 优先开放授权与官方公开数据；遵守 robots 与限速；
3. 原始数据与清洗后数据分层存储（原始层 / 标准层 / 结果层）；
4. 如实标注数据范围与局限，不夸大"国民零食全覆盖"。

### 5.5 系统范围定义

以"能在开放数据中查到的零食标签记录"为样本范围，品类包括膨化食品、饼干糕点、糖果巧克力、坚果炒货、肉类零食等；以数据实际覆盖范围为准，不做全量市场承诺。

## 7 数据库设计需求

### 7.1 总体架构：三层数据模型

| 层 | 内容 | 说明 |
|---|---|---|
| 原始层 | `raw_record` | API 返回的原始 JSON，不修改，用于溯源与重新解析 |
| 标准层 | 产品、品牌、品类、标签、配料、添加剂 | 清洗、去重、标准化后的数据 |
| 知识与结果层 | `user_rule`、`interpret_run`、`interpret_result`、`inspection_record` | 表驱动的解读与结果留痕 |

### 7.2 设计要求

| 编号 | 要求 |
|---|---|
| DB-1 | 设计满足第三范式（3NF）；统计字段可适度反范式化并说明理由 |
| DB-2 | 所有关系通过外键保证参照完整性；关键字段设 NOT NULL/UNIQUE/CHECK |
| DB-3 | 索引：`product(barcode)`、`product(brand_id,category_id)`、`product_ingredient(ingredient_id)`、`product_ingredient(product_id,position_no)`、`ingredient_alias(alias_name)`、`interpret_result(run_id,info_type)` |
| DB-4 | 表驱动：用户关注规则与知识条目存于表中，不写死在程序里 |
| DB-5 | 版本化：规则以版本区分，解读结果记录所用版本 |
| DB-6 | 事务：导入合并、解析写入、批量解读使用事务，出错回滚 |
| DB-7 | 视图：产品配料宽视图、产品信息汇总视图、添加剂使用频次视图 |
| DB-8 | 存储过程/触发器（选做）：配料解析存储过程、采集日志统计触发器 |
| DB-9 | 分区/归档（选做）：原始层按月份或数据源分区 |
| DB-10 | 备份与恢复：提供备份脚本并演示恢复流程 |
| DB-11 | 性能验证：提供 EXPLAIN 执行计划对比，说明索引优化效果 |

### 7.3 数据库选型建议

MySQL 8 / PostgreSQL 为主库（PostgreSQL 对 JSON、全文检索、递归查询支持更好）；采集与解析用 Python（requests + pandas + 正则）；可选 DuckDB 处理批量下载数据。

## 8 业务流程

### 8.1 总体流程

```
登记数据源与规则
      ↓
创建采集任务（品类关键词 + 限速）
      ↓
多源网络采集（API 分页 / 公告附件）
      ↓
原始层 raw_record（原样留存）
      ↓
清洗与字段规范化 → 去重合并
      ↓
配料表解析 / 名称标准化 → 待确认队列
      ↓
标准层（product / label_info / product_ingredient）
      ↓
知识库与用户关注规则（表驱动）
      ↓
成分解读与个性化提示
      ↓
查询 / 对比 / 统计 / 导出
```

### 8.2 流程说明

| 步骤 | 说明 | 输入 | 输出 |
|---|---|---|---|
| 1 | 登记数据源与关注规则 | 数据源清单、用户关注项 | 数据源表、规则表 |
| 2 | 采集（限速、重试、断点续跑） | 品类关键词 | raw_record |
| 3 | 清洗 | raw_record | 规范化数据 + 质量标记 |
| 4 | 整合 | 清洗结果 | product、label_info |
| 5 | 解析 | ingredient_text | product_ingredient |
| 6 | 解读 | 标准层 + 规则层 | interpret_result |
| 7 | 查询分析 | interpret_result | 图表、报告、导出 |

### 8.3 解读子流程

```
取一件产品
   ↓
配料表为空？ → 是：记录"配料信息缺失"（客观事实）
   ↓ 否
拆分配料 → 添加剂识别 → 名称标准化
   ↓
映射成功？ → 否：进入待确认队列
   ↓ 是
生成成分解读（客观事实 + 知识科普）
   ↓
命中用户关注规则？ → 是：给出个人提示
   ↓
写入 interpret_result（记录规则版本与时间）
```

### 8.4 消费者前台筛选子流程（V2.2 新增）

```
消费者免登录进入前台应用区
   ↓
勾选过敏原 / 打开控糖控钠开关 / 自定义阈值（FR-9.2）
   ↓
读取标准层产品（配料、营养、致敏原）→ 按条件过滤（FR-9.3）
   ↓
对每个产品判定：字段缺失 → 归为"信息不足"，说明缺项（FR-9.4）
                命中关注项 → "不适合"，给出配料原文证据（FR-9.5）
                未命中       → "适合"，附来源 URL（FR-9.6）
   ↓
展示结果（适合优先）→ 可展开看配料 → 可勾选两款对比（FR-9.6/9.7）
   ↓
页面常驻免责声明（FR-9.8）
```

> 该流程与后台解读子流程（8.3）共享数据标准层与用户规则表，区别仅在交互入口与术语呈现。

## 10 约束、风险与验收

### 10.1 约束与假设

1. 公开网络数据不提供"是否违规"的真值，系统只做信息整理；
2. Open Food Facts 中国零食覆盖有限（实测 180 条），须多品类累加，并如实说明数据范围；
3. 众包数据质量不一，需质量标记与抽样核对；
4. 匿名 API 限速 15 req/min/IP，须实现限速、缓存、退避与断点续跑。

### 10.2 主要风险与对策

| 风险 | 对策 |
|---|---|
| 开放库中国产品少 | 多品类累加 + 抽检公告补充；如实标注范围，不夸大 |
| API 限速 503 / 主站不可用 | 限速 4 秒+、指数退避、缓存、断点续跑、配置化备份通道 |
| 配料名称不规范导致映射失败 | 别名词典 + 待确认队列 + 迭代更新 |
| 众包数据质量不一 | 质量标记 + 抽样人工核对 + 来源留痕 |
| 结果被误读为违法定性 | 三级表述，报告注明方法与局限，界面固定声明 |
| 授权与合规 | 遵守 ODbL 署名与站点条款，仅公开数据，限速访问 |

### 10.3 验收标准

| 编号 | 验收项 |
|---|---|
| A1 | 数据库建表脚本可执行，主外键、索引、视图完整 |
| A2 | 采集 300~500 条真实网络数据，质量指标达到 2.2 节目标 |
| A3 | 配料解析覆盖率经抽样验证达标，待确认队列可用 |
| A4 | 成分解读、查询、对比功能均能产出结果并可追溯到来源与规则 |
| A5 | 提供典型查询与统计 SQL 及性能优化对比（EXPLAIN） |
| A6 | 提交需求文档、设计文档、SQL 脚本、采集/解析代码、测试与演示材料 |
| A7 | 前台应用区演示：消费者免登录在 3 次点击内完成筛选；结果明确区分三态且信息不足产品不被误判为"适合"；命中原因可读（V2.2 新增） |
