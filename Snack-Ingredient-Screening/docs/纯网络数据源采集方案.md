# 纯网络数据源采集方案（不拍照录入版）

> 约束：不采用学生拍照/人工录入，全部数据从公开网络渠道获取。
> 本方案基于 2026-11-25 对 Open Food Facts 官方 API 的实际请求测试，数字均为实测值。

---

## 一、结论先行

**纯网络取数可行，且比拍照录入更适合作为"高级数据库"课程作业。**

原因：拍照录入看起来像手工活，而"用程序从公开 API 批量取数 + 限速重试 + 原始数据入库 + 清洗整合"是标准的 ETL 流程，正好命中数据库课程的数据采集、多源整合、数据质量等核心考点。

代价：必须接受一个事实——**公开网络上的中国零食数据没有想象中多**，所以项目定位要相应调整（见第六节）。

---

## 二、实测证据（这是方案的地基）

### 2.1 可用的 API 与实测结果

| 测试项 | 结果 |
|---|---|
| 端点 | `GET https://world.openfoodfacts.org/api/v2/search` |
| 认证 | **读取免注册**，但必须带自定义 `User-Agent`（如 `SnackDB/1.0 (email)`） |
| 中国零食存量 | `countries_tags=en:china&categories_tags=en:snacks` → **count = 180 条** |
| 返回字段 | `code`（条码）、`product_name`、`brands`、`ingredients_text`（中文配料表）、`nutriments`（完整营养）、`categories_tags`、`additives_tags` |
| 实测样条 | "经典原味薯片 / 乐事 / 马铃薯、植物油、经典原味调味料(含5'-呈味核苷酸二钠)、TBHQ" |
| 限速 | 15 req/min/IP，**实测连续请求会返回 HTTP 503** |
| 授权 | ODbL 开放数据库许可，须注明来源；数据为众包，不保证准确 |

### 2.2 一个必须知道的数量事实

- 用**正确**的筛选参数 `countries_tags=en:china` → 约 **180 条**中国零食（snacks 品类）
- 用**错误/不带国家筛选** → 返回全球零食约 **35 万条**

说明：中国零食在这个开放库里覆盖有限但**真实可用**（有中文配料表）；全球零食量极大。这决定了你们的取数策略必须是"中国零食为主 + 全球零食做扩展/对比"。

## 三、数据源组合（三源互补）

| 源 | 角色 | 获取方式 | 预期数量 |
|---|---|---|---|
| **Open Food Facts** | 主数据源 | API 按国家+多品类抓取 | 300~500 条中国零食（换多个 `categories_tags` 累加） |
| **市场监管总局抽检公告** | 规则验证样本 | 官网公告 Excel/PDF 附件解析 | 20~50 条（含检出值、标准限值） |
| **电商公开详情页** | 少量补充 | 人工核对 + 限速访问公开页 | 30~50 条，仅作演示补充，不作主力 |

**明确放弃**：大规模爬京东/天猫等电商。理由是反爬机制、页面结构易变、配料多为图片需 OCR、使用条款限制——对学生项目投入产出比极低，也不符合合规要求。

## 四、技术实现路线（可直接照做）

### 4.1 抓取脚本骨架（Python）

```python
import requests, time, json

HEADERS = {"User-Agent": "SnackDB/1.0 (student-course@example.com)"}
BASE = "https://world.openfoodfacts.org/api/v2/search"

CATEGORIES = [
    "en:snacks", "en:biscuits", "en:chocolates",
    "en:candies", "en:nuts", "en:crisps", "en:cookies"
]

def fetch(category, page, page_size=100):
    params = {
        "countries_tags": "en:china",
        "categories_tags": category,
        "page": page,
        "page_size": page_size,
        "fields": "code,product_name,brands,categories_tags,"
                  "ingredients_text,additives_tags,nutriments,"
                  "countries_tags,image_front_url"
    }
    r = requests.get(BASE, params=params, headers=HEADERS, timeout=30)
    if r.status_code == 503:          # 实测会触发
        time.sleep(60); return None   # 退避重试
    r.raise_for_status()
    return r.json()

def crawl():
    seen = set()
    for cat in CATEGORIES:
        for page in range(1, 6):
            data = fetch(cat, page)
            if not data: continue
            for p in data.get("products", []):
                if p["code"] in seen or not p.get("ingredients_text"):
                    continue
                seen.add(p["code"])
                save_raw(p)           # 原始 JSON 原样落库，不修改
            time.sleep(5)             # 限速：15 req/min → 每次至少 4 秒
```

### 4.2 工程要点（即数据库课程的考点）

- **限速与退避**：每请求间隔 ≥4 秒，遇 503 指数退避 → 对应 FR-1.3 采集任务"限速"要求
- **原始数据层**：抓取的 JSON 原样存入 `raw_record`，不修改 → 对应"原始层/标准层分离"
- **断点续跑**：`seen` 集合记录已抓条码，失败后可继续 → 对应 NFR-2 分批与断点续跑
- **去重**：以条码为主键 → 对应 FR-2.2 多源去重
- **日志**：记录起止时间、成功数、失败数、失败原因 → 对应 FR-1.5 采集日志
- **数据质量标记**：配料为空的跳过并标记，不直接删除 → 对应 FR-2.5

### 4.3 数据落地表（沿用需求文档数据字典）

```
raw_record       ← 原始 JSON、来源 URL、抓取时间、content_hash
crawl_task       ← 品类关键词、状态、成功/失败数
product          ← 条码、名称、品牌、品类（标准层）
label_info       ← 配料原文、营养成分 JSON、来源
additive / ingredient_dict / product_ingredient  ← 解析标准化结果
```

## 五、数据量预期与验收调整

| 指标 | 调整后目标 | 说明 |
|---|---|---|
| 产品总数 | 300~500 条 | 中国零食为主，多品类累加；不追 2000 |
| 配料表非空率 | ≥90% | 抓取时过滤空配料 |
| 来源可追溯 | 100% | 每条能指回 API 记录 URL + 原始 JSON |
| 标准化覆盖率 | ≥80%（抽样） | 别名映射 + 待确认队列 |
| 检索响应 | ≤1 秒 | 本地数据库加索引 |

**删掉"筛查准确率"指标**——纯标签数据没有判定真值，不设这个指标（这正是对老师质疑的正确回应）。

## 六、项目定位的连带调整（关键）

纯网络数据 + 中国零食仅 180 条这个事实，要求定位从"国民零食全量库"收窄为：

> **"基于开放数据的零食标签结构化与查询系统"**——以 Open Food Facts 的中国零食记录为核心样本，演示从多源采集、清洗整合、配料标准化到可查询数据库的全过程。

这样表达的好处：
1. 不夸大"国民零食全覆盖"，避免老师质疑数据代表性；
2. **数据采集与整合本身成为项目主体**——这正是数据库课程该做的事；
3. "开放数据 + 众包质量标记"是可以正面讲的技术特点，不是缺陷。

## 七、答辩时怎么回应老师

> "老师，我们放弃了拍照录入，采用全自动网络采集：以 Open Food Facts 开放 API 为主源，按国家和品类批量抓取带中文配料表的零食数据；因为该库对匿名请求限速 15 次/分钟，我们实现了分页抓取、缓存、限速退避和失败重试。实测中国零食有 180 条，我们通过多品类扩展和抽检公告补充，把规模做到 300~500 条真实数据。所有原始数据存入原始层保证可追溯。这样既解决了学生获取数据难的问题，又完整展示了数据库课程要求的多源采集、清洗整合、质量标记和事务处理。"

## 八、风险与对策

| 风险 | 对策 |
|---|---|
| 开放库中国产品少（实测 180 条） | 多品类累加 + 全球零食做对比样本；如实说明数据范围，不夸大 |
| 匿名限速 503（实测发生） | 限速 4 秒+ / 缓存 / 指数退避 / 断点续跑 |
| 众包数据质量不一 | 质量标记 + 待确认队列 + 抽样人工核对 |
| 主站偶发不可用 | 数据源配置化，预留静态批量下载通道作备份 |
| 合规性质疑 | 只用公开 API、遵守限速与 ODbL 署名；**不输出违法定性结论** |
